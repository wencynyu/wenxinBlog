## 架构特点

### 1. 微服务架构

```
优势:
- 独立部署: 每个服务可独立发布
- 技术异构: Go/Java可混合使用
- 故障隔离: 单个服务故障不影响全局
- 弹性扩展: 按需扩容特定服务

挑战:
- 服务发现: 需要注册中心
- 分布式事务: 最终一致性
- 监控复杂: 链路追踪
```

### 2. 读写分离

```
写操作 (Write):
- 通过Gateway路由到写库
- 强一致性保证
- 实时同步到读库

读操作 (Read):
- 读从库或缓存
- 最终一致性
- 高性能
```

### 3. 缓存策略

```
L1缓存: 本地缓存 (Caffeine/Guava)
L2缓存: Redis分布式缓存

缓存策略:
- Cache-Aside: 读时缓存
- Write-Through: 写时更新
- Write-Behind: 异步更新

失效策略:
- TTL: 自动过期
- 主动失效: 数据变更时
```

### 4. 消息驱动

```
Kafka 是项目唯一的消息骨干（未使用 RabbitMQ）:
- 博文发布 → blog-service 发布事件 → search-service 消费 → 更新 Elasticsearch 索引
- 用户行为事件 → analytics-service / recommendation-service 消费
- 跨服务解耦、最终一致性
```

### 5. 可观测性

```
统一的 OpenTelemetry 管道（非碎片化）:
- 采集: Java 服务挂 OTel Java Agent；Go 服务用 OTel SDK
- 聚合: OTel Collector (4317/4318) 统一接收，批处理后导出
- 存储/展示:
  - Traces + Logs → Elasticsearch data stream (traces-apm-default / logs-generic.default)
  - Metrics → Prometheus (Collector 在 8889 暴露) → Grafana
- Grafana 看板: overview / logs / traces / api
```

## 扩展性设计

### 水平扩展

```yaml
# Kubernetes HPA (水平自动扩展)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: blog-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: blog-service
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
```

### 垂直扩展

```yaml
# 根据负载调整资源配置
resources:

```

## 高可用设计

### 服务高可用

```
- 多副本部署 (3+)
- 健康检查
- 自动重启
- 滚动更新
- 就绪探针
```

### 数据库高可用

```
PostgreSQL:
- 主从复制 (1主2从)
- 自动故障转移
- 读写分离

Redis:
- 哨兵模式 / 集群模式
- 自动故障转移
- 数据分片
```

### 跨可用区部署

```
Zone A: 主节点 + 2个副本
Zone B: 2个副本 (故障时接管)
Zone C: 备份 + 灾备
```
